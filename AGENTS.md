# Remote Devices MCP — инструкции агентам

## Принципы
- Работать с этим репозиторием: это модифицированный Remote Harness MCP, база upstream 0.4.8.
- Общаться с пользователем по-русски. KISS: минимум зависимостей и инфраструктуры; существенное усложнение сначала обсуждать.
- Не добавлять совместимость со старыми клиентами без явного требования. Не заменять нашу версию автоматическим обновлением из upstream.
- Проверять `git status`: в рабочей копии есть незакоммиченные изменения. Сохранять чужую работу.
- Изменения кода сами по себе не означают разрешения на деплой. Для конкретной задачи учитывать актуальные указания пользователя.

## Архитектура и код
- **Одно устройство — один отдельный MCP-коннектор ChatGPT**, собственная идентичность и ключи. Не объединять устройства в общий коннектор.
- `gateway.py`: публичный HTTP MCP `/mcp`, classic SSE `/sse`, pairing, registry и исходящие WSS-туннели агентов.
- Туннели хранятся в памяти: **ровно один Gateway worker**. Несколько процессов с независимыми таблицами туннелей не поддерживаются; есть файловая блокировка.
- `core/agent.py`: агент; `core/mcp_tools.py`: инструменты; `core/onboarding.py`: `pair`, `status`, `link`; `install.sh` / `install.ps1`: установка и службы.
- Pairing требует подтверждения администратора. Короткий код дополняется секретом `X-Pair-Secret`; TTL 10 минут, незавершённые сессии теряются при рестарте Gateway.
- Полноценных аккаунтов/OAuth нет: `user` в URL — идентификатор устройства. Device token, link key и admin token имеют разные назначения; admin key владельцам устройств не выдавать.
- Коннектор: `https://<gateway>/mcp?user=<device>&token=<link_key>`, в ChatGPT — No authentication; ключ проверяет Gateway.
- Не повторять автоматически изменяющую команду после потери ответа. `readOnlyHint` должен соответствовать реальному поведению инструмента.

## Проверки и секреты
- Использовать существующий `.venv`; зависимости Gateway — `requirements-gateway.txt`, интеграций — `requirements-integration.txt`.
- Пример локальных проверок: `.venv/bin/python -m pytest -q tests/test_onboarding.py tests/test_onboarding_live.py tests/test_gateway_single_process.py`.
- `test_onboarding_live.py` поднимает локальный HTTPS Gateway и реальные WSS-агенты, проверяет привязку двух устройств, выполнение команд и отзыв доступа.
- Для соответствующих изменений запускать профильные регрессии. Проверка `/health` или `tools/list` не доказывает доступность устройства: нужен реальный `tools/call`, например `mesh_status`.
- `tools/verify_live_mcp.py` выполняет реальные команды и запись/чтение файла на целевом узле; выбирать устройство осознанно. Нативный Windows-сценарий ранее не проверялся.
- `.state/` приватна, исключена из git и содержит действующие токены. Не публиковать её содержимое, полные URL коннекторов, `agent.env`, registry или сырые логи без проверки на секреты.

## TECNO / Termux: установленное ограничение
- TECNO LI6, Android 15, сборка `LI6-15.1.2.170SP05(OP001PF001AZ)`, Termux 0.118.3.
- При сворачивании Transsion/HiOS **Hiber** замораживает UID Termux примерно через 5 секунд, затем закрывает сокеты. Процессы сохраняются и возобновляются при открытии приложения.
- Проверены без успеха: unrestricted battery, HiOS «Без ограничений», подтверждённый wakelock, перезагрузка, закрепление в Recents. Смена транспорта не исправит остановку исполнения.
- Подтверждена ошибка исключений: Hiber передаёт результат `getNameForUid()` (`com.termux:10143`) в `getPackageInfo()`, получая `NameNotFoundException`. Сохранённый `mode=1` не доказывает применённое исключение; runtime-команда тоже может ложно вернуть успех.
- Диагностика: `adb shell dumpsys tran_bootstrap_service_manager tran_usf -hiber is_white_app com.termux` (аналогично `com.termux.api`); окончательная проверка — состояние cgroup и реальные команды при свёрнутом приложении. UID/PID получать заново.
- Конфиг `/product/tranusf/config/hiber/hiber.json` доступен только для чтения; `-load_config` в исследованной сборке — заглушка. В разобранных JAR внешний вход с настоящим packageName для runtime-исключения не найден; это не доказательство требования root.
- Пользователь **не разрешает root, глобальное отключение энергосбережения и не хочет переустанавливать Termux**. Рабочего обхода пока нет.
- Пользователь сообщил об отправке багрепорта в поддержку. Текст и локальный разбор: `.state/hiber-diagnostic/TECNO-Hiber-bug-report.txt` и соседние файлы. Ждём ответ/номер обращения; не утверждать, что ошибка исправлена.
