# Подключение устройств через Google: основа в репозитории

Реализация развёрнута на VPS 2026-11-10. Google OAuth client настроен. Сквозные проверки
Google, браузера, установки на Ubuntu 26.04 и Windows отложены по указанию
пользователя. Историческое описание работающей версии с административным
подтверждением находится в `ONBOARDING_DEPLOYMENT.md`.

## Пользовательский сценарий

1. Пользователь запускает опубликованный установщик. Он сразу сообщает о запуске,
   показывает загрузку каждого компонента и периодические сообщения при долгих
   операциях в shell. Ошибка загрузки останавливает установку с названием файла.
2. Установщик спрашивает, приступить ли к авторизации через браузер. Enter или любой ответ, кроме `нет`/`no`/`n` без учёта регистра, открывает готовую ссылку заявки. При отсутствии терминала ссылка открывается пользователем вручную. **Код вводить не нужно.**
   При отсутствии браузера эту ссылку можно открыть на другом устройстве.
3. В браузере пользователь входит через Google, проверяет название устройства и
   явно нажимает «Подключить устройство». Вход сам по себе ничего не привязывает.
4. Gateway сохраняет владельца, выдаёт отдельные device token и link key.
   Установщик забирает ключи только с длинным `X-Pair-Secret`, сохраняет их
   приватно и запускает существующую платформенную службу агента.
5. Установщик проверяет реальный `tools/call mesh_status`. Только после ответа
   устройства выводит готовый Server URL для отдельного коннектора ChatGPT с
   `No authentication`. Google OAuth используется только в кабинете Gateway.
6. `/account` показывает только устройства вошедшего владельца. Там можно
   скопировать ссылку, проверить реальный ответ агента, заменить ссылку или
   отозвать доступ. Замена и отзыв требуют отдельного подтверждения.

Внешний вид: светлая палитра, полупрозрачные панели с `backdrop-filter`, мягкие
переливы, адаптивная вёрстка, нативные `details` и Clipboard API с ручным
копированием при отказе. Без CDN, фронтенд-фреймворка и сборки.

## Минимальная архитектура

- `gateway_identity.py`: серверный Google Authorization Code flow, PKCE S256,
  state, nonce, проверка подписанного ID token официальной `google-auth`.
- `gateway.py`: подтверждение заявки и кабинет; существующие registry, туннели,
  проверка device token/link key и административный API.
- Владелец — `owner_subject = google:<sub>` в записи устройства. Email используется
  для отображения, не для проверки принадлежности. Смена email не меняет владельца.
- Устройство получает уникальный идентификатор и собственные ключи. Совпадающее
  имя другого устройства создаёт новую запись с суффиксом.
- Никакой новой БД, Redis, аккаунтов с паролями или общего MCP-коннектора.
- Opaque browser sessions живут в ограниченной памяти одного Gateway worker
  восемь часов. Cookie: `__Host-`, Secure, HttpOnly, SameSite=Lax, Path=/.
  Выход удаляет серверную сессию; рестарт завершает все браузерные сессии.
- Все изменяющие действия кабинета требуют CSRF token и проверяют Origin,
  если браузер его передаёт. Право владельца проверяется на сервере при каждом
  действии. Cookie входа не принимается как доступ к MCP или WSS.
- Вход ограничен по IP, число незавершённых входов и сессий ограничено.
  Сетевые обращения к Google выполняются вне event loop с таймаутами и лимитом
  параллелизма. Authorization codes, access/refresh/ID tokens не сохраняются.
- HTML не кэшируется; CSP запрещает встраивание страницы и посторонние скрипты;
  `Referrer-Policy: strict-origin` на HTML-страницах (без пути и query); OAuth redirects используют `no-referrer`. Uvicorn-фильтр скрывает token, code и state.
- Заявка действует 10 минут и теряется при рестарте. Повтор получения ключей не
  создаёт вторую запись. Истёкшая/утраченная заявка удаляется установщиком при
  следующем опросе; повторный запуск создаёт новую. Отозванная заявка ключей
  больше не выдаёт.
- При включённом Google OAuth анонимный `/api/register` закрывается независимо
  от прежнего `MESH_REGISTER_MODE`. Вход не позволяет присвоить существующую
  запись без владельца. Административный API остаётся серверным способом
  сопровождения, его секрет не запрашивается на странице привязки.

## Подготовка Google OAuth

В Google Cloud создать OAuth client типа **Web application**, настроить
брендинг/аудиторию приложения и добавить точный Authorized redirect URI:

```text
https://mcp.natureonzoom.win/auth/google/callback
```

Для другого домена заменить origin; он должен совпадать с `MESH_PUBLIC_URL`.
При работе OAuth-приложения в режиме Testing добавить нужных тестовых пользователей.
Для публичного использования отдельно завершить требуемую Google настройку
публикации приложения. Запрашиваются только `openid email`, доступ к Drive и
другим Google API не требуется. Client secret не присылать в чат и не включать
в установщик или git.

На сервере записать в `/etc/remote-harness-mcp/gateway.env`:

```dotenv
MESH_GOOGLE_CLIENT_ID=<Web OAuth client ID>
MESH_GOOGLE_CLIENT_SECRET=<Web OAuth client secret>
MESH_REGISTER_MODE=pair
```

Пустые обе Google-переменные отключают пользовательский вход. Если задана
только одна, Gateway останавливается при запуске с понятной ошибкой конфигурации.
Без настройки Google страница показывает причину, не предлагает ввод admin key.
Существующие устройства продолжают использовать свои ключи.

Для будущего развёртывания нужны `gateway.py`, **`gateway_identity.py`**,
`requirements-gateway.txt`, обновлённые установщики и `core/onboarding.py` вместе
с остальным текущим payload. В существующем серверном venv установить
`requirements-gateway.txt`. Старый `deploy_gateway.sh` не адаптирован к текущей
VPS-инфраструктуре; запускать его для этой задачи не следует.

Перед включением проверить, что reverse proxy не сохраняет query-параметры
`token`, OAuth `code`, `state` в access log. Не переносить секреты из registry
в вывод диагностики. Перезапуск Gateway кратковременно разрывает WSS и сбрасывает
ожидающие заявки, поэтому это отдельный согласованный этап.

## Проверки следующего этапа

- Реальный Google login: успешный вход, отказ пользователя, неверный/повторный
  state, неверный nonce/audience/issuer/подпись, истечение срока и ошибки Google.
- Два разных Google-владельца и два одинаково названных устройства: независимые
  ключи, отсутствие чужих ссылок в кабинете, запрет чужих действий и CSRF.
- Вход не подтверждает заявку автоматически; повтор подтверждения владельцем
  не создаёт вторую регистрацию; другой пользователь не может присвоить её.
- Реальные HTTPS/WSS-агенты: mesh_status, выполнение команды, запись/чтение,
  замена link key, отзыв активного соединения, запрет старых ключей.
- Повтор установщика, потеря ответа, истечение заявки и перезапуск Gateway;
  сохранение старой конфигурации; загрузка только с нашего Gateway без upstream.
- Терминал Ubuntu: немедленный статус, долгий DNS/загрузка/pip, прерывание,
  недостающий файл, понятная ошибка. Отдельный нативный прогон Windows.
- Браузер: 375px и desktop, клавиатура, копирование с разрешением и без него,
  формы подтверждения и отзыва, отсутствие секретов в логах/кэше.

Официальные источники: [Google OpenID Connect](https://developers.google.com/identity/openid-connect/openid-connect),
[проверка ID token в google-auth](https://google-auth.readthedocs.io/en/latest/reference/google.oauth2.id_token.html).

## Переход на собственный домен выполнен

Основной Gateway: https://mcp.natureonzoom.win . Cloudflare DNS A:
`mcp.natureonzoom.win` → `108.181.252.78`, DNS only, TTL 300.
В существующем Caddy добавлен host с `tls force_automate` для публичного
сертификата вместо wildcard Cloudflare Origin других сайтов.

Пользователь заменил callback в Google Console на
`https://mcp.natureonzoom.win/auth/google/callback`.
Обновлены MESH_PUBLIC_URL Gateway и конфигурация VPS-агента.
Старый hostname временно обслуживает существующие MCP/WSS-подключения;
браузерные страницы онбординга перенаправляются на новый домен.
Для ранее созданных коннекторов замените только origin Server URL,
сохранив путь и индивидуальные user/token. Новая регистрация не требуется.
Телефон techno требует отдельной миграции адреса в его локальной конфигурации.
