# Развёртывание обновлённой привязки устройств

> Исторический отчёт о версии с административным подтверждением. Новая основа
> Google OAuth развёрнута 2026-11-10, ожидает настройки клиента и ещё не прошла
> сквозное тестирование: [GOOGLE_OWNER_ONBOARDING.md](GOOGLE_OWNER_ONBOARDING.md).

Рабочий Gateway: https://rhm.108-181-252-78.sslip.io
VPS: 108.181.252.78. Код: /opt/remote-harness-mcp.
Процесс: rhm-gateway.service, systemd, один worker, без нового контейнера.
Используется существующий HTTPS reverse proxy Caddy. Его конфигурация не менялась.

Развёрнут проверенный сценарий **с подтверждением администратора**:

1. Установщик показывает код и ссылку /pair?code=… .
2. Администратор открывает ссылку, сверяет код/устройство и подтверждает своим ключом.
3. Установщик забирает индивидуальные ключи, автоматически сохраняет настройки,
   использует существующий запуск служб и проверяет реальный MCP mesh_status.
4. Пользователь получает отдельный /mcp?user=…&token=lk_… для своего устройства.
   В ChatGPT выбирает No authentication: серверный ключ уже включён в URL.

Ключ администратора НЕ нужно передавать владельцу устройства. Он хранится в
/etc/remote-harness-mcp/gateway.env на VPS. Страница не хранит его в браузерном
хранилище и отправляет только в заголовке запроса подтверждения.

Опубликованы /install.sh, /install.ps1 и необходимые исходные файлы агента.
Установщики, полученные с этого Gateway, включают pairing по умолчанию и уже
знают адрес Gateway. В репозитории pairing включается --pair / -Pair.
Произвольные файлы, конфигурации и registry не публикуются.

Изменения: core/onboarding.py, установщики, защищённый сбор ключей через
X-Pair-Secret, страница подтверждения и ограниченная выдача исходных файлов.
Короткий код сам по себе не позволяет получить учётные данные. Повтор запроса
получения с длинным секретом до истечения TTL не создаёт новое устройство.
Код действует 10 минут. Незавершённые pairing-сессии находятся в памяти:
после рестарта Gateway потребуется начать привязку заново. Для установленного
новым установщиком устройства повтор установки использует сохранённую идентичность.
Автоматические обновления адаптированного агента из upstream отключены.

Миграции старых конфигураций и новые слои обратной совместимости не добавлялись.
Полноценные аккаунты, OAuth, приглашения и свободная регистрация не реализованы.
Самостоятельное подключение без участия администратора пока не закончено.
Команда статуса: python -m core.onboarding status .
Команда показа ссылки после реальной проверки: python -m core.onboarding link .
Windows-код обновлён, но нативного запуска Windows-установщика в этой среде не было.
Способ запуска после перезагрузки остаётся платформенным: systemd/runit/Windows
Startup + watchdog. Android по-прежнему требует системных разрешений и корректных
настроек фоновой работы Termux/Termux:Boot; установщик не может выдать их сам.

Проверено перед деплоем: 256 passed, 16 skipped (включая Windows-зависимые проверки).
После деплоя по публичному HTTPS: новый pairing, защищённая выдача ключей, настоящий
WSS-агент на рабочей машине, mesh_status, shell-команда, запись/чтение уникального
маркера, получение установщиков и отзыв доступа. Временный агент остановлен,
регистрация отозвана. SHA256 gateway.py, core/onboarding.py и обоих установщиков
на VPS совпадают с рабочей копией. Проверки реальных вызовов внутри интерфейса
ChatGPT именно после этого обновления не проводились.
