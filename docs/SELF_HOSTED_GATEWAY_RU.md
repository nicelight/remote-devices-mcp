## Адрес и подключение ChatGPT

Публичный `/health` возвращает только `{"status":"healthy"}`.
Полный URL действующего узла `vps-node` находится в локальном приватном файле
`.state/chatgpt-vps-url.txt` (права 0600). Секретов в этом документе нет.

В настройках пользовательского MCP-сервера ChatGPT вставить **всё содержимое этого
файла** в поле Server URL и выбрать **No authentication**: Gateway проверяет
индивидуальный link key в самом URL. Формат:
`https://<gateway>/mcp?user=vps-node&token=lk_<secret>`.
Без ключа `/mcp` намеренно отвечает 401. Обновить список инструментов после подключения.
Проверочные запросы: «Вызови mesh_status», затем «Выполни bash_exec с командой id».
Узел работает как `rhm-node`, без sudo и права менять системные файлы.
Для другого устройства выдаётся собственный URL и отдельный коннектор.

Streamable HTTP `/mcp` — основной транспорт; классический SSE `/sse` также проверен.
Вызовы через интерфейс ChatGPT ещё **не подтверждены**: в доступном окружении нет
браузера/авторизованной сессии ChatGPT. Наличие работающего MCP SDK не доказывает
устранение исходного сбоя именно на стороне ChatGPT.
[Официальная инструкция подключения](https://developers.openai.com/api/docs/guides/custom-mcp-server).

## Архитектура и размещение

Интернет → существующий Caddy:443 → `172.19.0.1:8096` → один Python Gateway.
Агенты сами открывают исходящие WSS-соединения на 443; публичный IP устройства
и входящие порты на нём не требуются. Новый Docker-контейнер не создавался.
Caddy уже существовал в Docker; его конфигурация дополнена одним виртуальным хостом.

| Назначение | На VPS |
|---|---|
| Код и Python 3.11 venv | `/opt/remote-harness-mcp` |
| Gateway | `rhm-gateway.service`, пользователь `rhm-gateway` |
| Данные и registry | `/var/lib/rhm-gateway`, права каталога 0700 |
| Настройки и admin/enrollment secrets | `/etc/remote-harness-mcp/gateway.env`, 0640 root:rhm-gateway |
| VPS агент | `rhm-node.service`, пользователь `rhm-node` |
| Workspace и конфигурация агента | `/var/lib/rhm-node`, `agent.env` 0600 |
| Reverse proxy | `/opt/caddy/Caddyfile` |
| Копии конфигурации и registry | `/root/rhm-private/`, исходный Caddyfile — рядом с ним под именем `Caddyfile.pre-rhm-*` в `/opt/caddy` |

Обе службы включены в автозагрузку. systemd запрещает им повышение привилегий,
делает системные файлы read-only, скрывает домашние каталоги и разрешает запись
в собственный каталог состояния. Gateway слушает только bridge-интерфейс хоста,
на публичном интерфейсе новый порт не открыт. Адрес bridge в unit передаётся через
`MESH_LISTEN_HOST`; при замене сети существующего Caddy его нужно актуализировать.

## Изменения кода

- Агент посылает device token в Authorization: Bearer, поддерживая старое и новое
  имя параметра headers в websockets. Device token больше не добавляется в URI.
- Честные readOnlyHint; shell-команды дополнительно помечены potentially destructive
  и open-world. Подсказки больше не обещают обход подтверждений клиента.
- При разрыве туннеля изменяющие операции не повторяются автоматически:
  потерянный ответ не означает, что команда не выполнилась.
- Межпроцессный flock не позволяет нескольким worker-процессам использовать
  один registry с несогласованными таблицами туннелей. Это защита от ошибочной
  конфигурации, а не распределённая система: несколько VPS/разных registry
  потребуют отдельной архитектуры маршрутизации.
- Registry записывается атомарно с правами 0600; повреждённый registry не
  интерпретируется как пустой. Путь конфигурируется окружением.
- Логи Gateway не содержат аргументы инструментов; access log uvicorn выключен.
  На добавленном Caddy vhost access logging не включался.
- Подробный health закрыт, добавлен ID экземпляра для диагностики.
- Исправлены OPTIONS /mcp и classic SSE: отдельный stream_id в endpoint,
  ответы идут в конкретный поток, HTTP POST подтверждается 202.
- Исправлена фикстура Termux-тестов: pkill заменяется заглушкой, чтобы тестовая
  установка не завершала реальный локальный агент.
- Для наших узлов отключены автоматическая проверка/установка upstream-обновлений,
  чтобы они не перезаписали адаптированный код.

## Обслуживание

```bash
ssh igorprod 'systemctl status rhm-gateway rhm-node --no-pager'
ssh igorprod 'journalctl -u rhm-gateway -u rhm-node -n 100 --no-pager'
```

Перезапуск Gateway разрывает туннели на несколько секунд, агенты восстанавливаются:

```bash
ssh igorprod 'systemctl restart rhm-gateway'
```

Для повторения интеграционных тестов из рабочей копии:

```bash
.venv/bin/python tools/verify_live_mcp.py .state/vps-node.json --output .state/verification.json
.venv/bin/python tools/verify_live_mcp.py .state/vps-node.json --output .state/verification-sse.json --transport sse
.venv/bin/python tools/verify_live_mcp.py .state/vps-node.json --output .state/verification-bearer.json --auth bearer
```

Набор тестов записывает только файл `integration-proof.txt` в workspace узла.
Зависимости для отдельной машины проверок — `requirements-integration.txt`.
Шаблоны действующих служб и конфигурации — `ops/systemd/`.
Старый `deploy_gateway.sh` рассчитан на другое серверное окружение; не запускать
его на этом VPS без адаптации к Caddy и каталогу состояния.

## Подключение следующего устройства и TECNO

Подготовлен архив `dist/remote-harness-node-custom.tar.gz`: core, skills,
`tools/enroll_node.py`, зависимости. Секретов в нём нет.
На Linux/Termux распаковать его в отдельный каталог, установить websockets
(на Linux удобно создать venv; в Termux использовать его штатный Python).
Передать **только** enrollment secret в приватный файл на целевом устройстве.
Локальная копия секрета находится в `.state/enroll-secret.txt`; admin token устройству не нужен.

```bash
python tools/enroll_node.py \
  --gateway https://rhm.108-181-252-78.sslip.io \
  --name techno --enroll-secret-file /path/to/private-enroll-secret \
  --config-dir ~/.config/rhm-selfhost
MESH_CONFIG_FILE="$HOME/.config/rhm-selfhost/agent.env" python -m core.agent
```

Скрипт не перезаписывает существующий agent.env, сохраняет device token и
персональный ChatGPT URL с правами 0600. После успешной проверки можно заменить
команду запуска существующей службы runit на новый каталог и MESH_CONFIG_FILE.
Сначала нужно сохранить старую конфигурацию телефона для отката. Значения старого
MESH_PUBLIC_URL/domain.env не должны перекрывать новый адрес.
Termux:API должен быть установлен и разрешения Android выданы, как в текущей
установке телефона; существующие настройки MESH_DEVICE* переносятся отдельно.

Телефон **ещё не перенесён и не протестирован**: доступ к Termux, его действующий
MCP URL и device token в этой сессии не предоставлены. Старая регистрация techno
на сервере автора не переносится автоматически в наш независимый registry.

## Ограничения

- Причина Issue #3 на сервере автора не установлена. Мы подтвердили локальную
  работоспособность собственной инфраструктуры и исправили отдельный SSE-дефект,
  но не доказали, что именно он либо несколько worker-процессов вызвали тот инцидент.
- Конечная проверка вызова из ChatGPT и телефона остаётся обязательной.
- Link key в URL даёт управление соответствующим узлом. OAuth не реализован;
  такой URL нужно хранить как пароль. При утечке отозвать/ротировать link key.
  Старый query-token режим WebSocket оставлен для совместимости с upstream-агентами,
  наши агенты используют заголовок. Поддержка legacy сама по себе не означает,
  что старые устройства уже мигрировали на защищённую передачу.
- sslip.io — внешний DNS-сервис; для постоянной эксплуатации лучше свой домен.
- Проверены короткие команды, параллельность и restart, но не длительный soak-test,
  перезагрузка VPS или Android Doze/смена Wi-Fi и мобильной сети.
- Классификатор shell-команд — маршрутизация, не изоляция. За реальные права
  отвечают пользователь ОС и sandbox службы. VPS-узел не даёт root-доступ.
- Есть начальные резервные копии, но регулярное внешнее резервирование registry
  ещё не настроено. При потере registry устройства придётся регистрировать заново.
